# План: шифрование резервных копий с выбором пароля

**Решение по умолчанию:** шифрование **опциональное**. При экспорте пользователь
может задать пароль; без пароля формат остаётся прежним (обратная совместимость).
Импорт сам определяет зашифрованный файл и запрашивает пароль.

**Ограничения:** без новых зависимостей (только `javax.crypto`), пароль нигде не
сохраняется и не логируется, существующие бэкапы v1–v4 импортируются как раньше.

## Формат

JSON-конверт, отличимый от обычного бэкапа полем `enc`:

```json
{"app":"detour","enc":1,"kdf":"PBKDF2WithHmacSHA256","iter":600000,
 "salt":"<b64 16B>","iv":"<b64 12B>","ct":"<b64 ciphertext+GCM tag>"}
```

- AES-256-GCM; заголовок (`app`, `enc`, `kdf`, `iter`) идёт в AAD, чтобы его
  нельзя было подменить.
- Соль и IV случайные на каждый экспорт.
- Верхняя граница `iter` при чтении (защита от DoS чужим файлом).
- Неверный пароль и повреждённый файл различаются: GCM-тег не сошёлся → «неверный пароль».

## Этапы (после каждого — пауза и отчёт)

1. **Криптоядро** `core/BackupCrypto.kt` (чистый JVM) + unit-тесты: round-trip,
   неверный пароль, подмена заголовка/шифртекста, разные соль/IV, лимит `iter`,
   не-конверт.
2. **Интеграция в формат**: `SettingsBackup`/`BackupDocumentIo` — определить
   зашифрованный документ, учесть лимит размера (base64-оверхед), тесты.
3. **ViewModel**: экспорт с необязательным паролем, импорт с запросом пароля,
   новые статусы (`NEEDS_PASSWORD`, `WRONG_PASSWORD`), тесты.
4. **UI**: диалог пароля (экспорт: пароль + подтверждение, можно пропустить;
   импорт: ввод пароля), строки en/ru, доступность.
5. **Документация**: README/README.ru, CHANGELOG, SECURITY, `docs/features.md`;
   итоговая сверка.

## Проверка

Сборка Android в этой среде недоступна (нет SDK). Для этапа 1 крипто-логика
чистая JVM, поэтому запускаю тесты напрямую через `kotlinc`/JUnit, если
доступны; остальное проверит CI.
